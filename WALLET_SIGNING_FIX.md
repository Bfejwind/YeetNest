# Wallet Signing Adjustments

Confirmed Phantom cause: it appends a Lighthouse guard to the unchanged claim. Validator now permits up to eight trailing assertion instructions from the pinned Lighthouse program ID, variants 6 (AccountInfoMulti), 9 (TokenAccount) and 10 (TokenAccountMulti), on already-reviewed accounts without new permissions. Memory-write/close instructions, other programs, arbitrary new accounts and changes to original economic instructions remain rejected. Guards are preserved for signed simulation and broadcast, not stripped. See https://docs.phantom.com/developer-powertools/lighthouse and https://github.com/Jac0xb/lighthouse/blob/main/programs/lighthouse/src/instruction.rs .

Creator claims and swaps now use a shared check for wallet-adjusted messages. This supports blockhash, bounded ComputeBudget limit/price updates and the trailing Lighthouse assertions described above. Economic instruction bytes, ordered recipients/accounts and fully resolved signer/writable permissions must remain identical. Accounts may relocate between lookup and static storage only after resolving both reviewed and returned lookup tables and proving address/permission equivalence. Conflicting duplicate permissions, new economic accounts, extra signers and changes to launch transactions remain blocked.

An adjusted transaction must have a valid blockhash, estimated total network fee no greater than 0.01 SOL, and a successful signed simulation. Claims and trades allow at most 1,400,000 compute units; claim builders initially request 400,000. Unknown compute instructions and duplicates are rejected. Rejection diagnostics report instruction equivalence and compute-budget differences without exposing private keys or provider credentials.

Unchanged Jupiter transactions retain provider execution. Adjusted, single-signer Jupiter swaps are broadcast through the configured RPC after validation and simulation, because the original managed request was constructed for a different message. Routes requiring other signatures cannot be safely modified and remain rejected. This does not finish the project's broader Jupiter route-economic audit; it preserves the reviewed provider instructions rather than decoding all router semantics.

Deploy both frontend and web backend (including the isBlockhashValid RPC allowlist), then prepare fresh quotes/claims. No new migration is needed for this signing change; pending capacity changes still require their own migration. No funded transaction was submitted during verification.

Focused tests: `node --test tests/claim-message.test.js`; mocked browser signing check: `npx playwright test tests/ui/signed-adjustment.spec.js`. Browser fixtures sign disposable test keys and mock RPC broadcast; they do not prove Phantom mainnet acceptance.
